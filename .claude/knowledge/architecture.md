# Architecture

Learning-oriented 2D game engine in C# (.NET 10, Windows), designed so 3D can be added later. Goal: understand how engines work, so core systems are written from scratch and libraries are used only for plumbing (windowing, GL bindings, image decoding, debug UI).

        ├──► Engine.Physics2D ────────────────────────────────────┤
        ├──► Engine.Scenes ──► Engine.Core   (Runtime also depends on Scenes, Physics2D, Tilemaps, Animation, Audio)
        ├──► Engine.Audio ──► Engine.Core

Rules: Core never references Platform, Rendering or Silk.NET. Layers depend on abstractions at their boundaries (input is `InputState`/`ActionMap`, not Silk types).

Shared build config is in `Directory.Build.props` (net10.0, nullable, implicit usings; for non-test projects XML docs + StyleCop `SA1402`, with `CS1591` and `SA1402` as errors). Analyzer severities are in `.editorconfig`.

## Frame data flow

Per display frame (`Game.OnUpdate` then `Game.OnRender`, driven by Silk's window loop):

1. Window events fill `InputState` (via `SilkInputAdapter`; key/mouse presses are dropped while ImGui wants the input, releases always pass).
2. `FrameSystems` run, then `Game.Update` (read input here, latch intent into components, e.g. `PlayerInputSystem` writes `PlatformerIntent`).
3. `FixedTimestep.Advance(dt)` returns N steps; for each: `FixedSystems`, then `Game.FixedUpdate`. The sample's first fixed system is `PreviousTransformSystem` (records each `PreviousTransform` before the step moves anything).
4. `Input.EndFrame()` clears pressed/released edges and scroll.
5. Render: `Game` sets `RenderClock.Alpha` (the timestep's 0..1 fraction), then `PostProcess.BeginScene()` (redirects drawing into the scene target only if some effect is enabled), `Game.Draw` (resets batch stats, clears), `RenderSystems` in registration order (sample: background/ground `TileLayerRenderSystem`, `SpriteRenderSystem` which gathers `Transform`+`Sprite` and sorts back-to-front by Z then texture, foreground `TileLayerRenderSystem`; each pass is its own `SpriteBatch.Begin/End`), then `PostProcess.EndScene()` (runs the enabled effects, the last one writing to the window), then the ImGui overlay (`DebugOverlay` + `Game.DebugGui`), which is drawn after the effects so tools are never darkened or bloomed.

Shutdown: GPU cleanup happens in the window's `Closing` event, **while the GL context still exists**: `GameWindow.OnClosing` raises `Closing` (so `Game` runs `Unload()` then `Assets.Dispose()`), then disposes the ImGui controller and input. `Game.Dispose`/`GameWindow.Dispose` afterwards only release the managed GL bindings and the window. (Decision and reason: after `Run()` returns the context is destroyed and any GL delete throws `NoContext`; this crashed every normal window close until phase 7.)

## Scene editor (`src/Engine.Editor`, phase 21: a separate program)

**Decision (phase 21): the editor is its own executable**, `Editor.exe` (project `src/Engine.Editor`, assembly `Editor`), not a mode of the game window. Reasons: editing and playing are different jobs; the game window used to be covered by floating panels and the editor could not be opened without starting the game; a shipped game must not contain editor code; one editor opens any game. Run it with `tools/run-editor.ps1 -Game Platformer`, or `Editor <project>.csgame.json`, or `Editor` for the hub (see the projects section below).
- **Game = library + launcher.** `samples/Platformer` and `samples/Scene3D` are class libraries (`Platformer.Game.dll`, `Scene3D.Game.dll`, each with one `IGameModule`: `PlatformerModule`, `Scene3DModule`); `samples/*.Launcher` are the tiny exes that ship (`Platformer.exe`: `new PlatformerModule().CreateGame(GameLaunch.Default).Run()`), with no editor reference. The assets live in the library project and flow into the launcher's output through the project reference. Decision: the module only says "create the game with these folders"; `Game` stays the composition root (components, systems, loaders registered in its constructor/`Load`), because a registration-only module would have meant rewriting every game's start-up for no benefit yet.
- **`GameLaunch`** (Runtime) says where a game finds its files: `Default` = next to the executable; `ForProject(folder)` = the project's source `Assets` folder (so saving a scene or tile layer changes files you can commit) and a `.local` folder for quick-saves and high scores. Games never read `AppContext.BaseDirectory` themselves.
- **The seam into `Game`**: `Game.AttachEditor` (internal; Runtime has `InternalsVisibleTo Editor`) takes a factory that receives an `EditorContext` (world, assets, the shared `EntityInspector`, log, `EditorHooks`, the `Game`) and returns an `IEditorShell` (`Active`, `Editing`, `BeginFrame`, `Toggle`, `Draw`) that the loop drives. `SceneEditor` is that shell (`Pinned` = the standalone editor never turns off). `GameLibrary.Load` loads the DLL (engine assemblies are the editor's own, the game's folder is resolved through its `.deps.json`) and instantiates the one `IGameModule`. Shared edit state used by the debug inspector (`EditorSelection`, the whole `Undo` command stack, `TileChange`) lives in `Engine.Runtime/Editing`, because `EntityInspector` needs it and the inspector stays in Runtime as the F1 debug overlay of a development run.
- **The scene panel**: the game is drawn into a texture and shown in a docked "Scene" panel. `PostProcessChain.UseOffscreenOutput(true)` (switched on the first time the editor calls `Game.SetViewport`) sends the finished image to `OutputTexture` instead of the window and restores the window framebuffer and GL viewport afterwards (**bug found in the window:** forgetting the viewport left ImGui drawing into a 530x1 area). `Game.SetViewport(origin, size)` records where the panel is: `ViewportWidth/Height` and the `ViewportResized` event replace the window size for cameras and HUD layout (`ViewportOrigin` shifts ImGui HUD windows into the panel), and `InputState.SetMouseOffset` makes `Input.MousePosition` relative to the panel, so game code reads the mouse in its own pixels. The game renders at least 64x64 even when the panel is tiny (post effects cannot make an empty image). While editing, `SceneEditor` works in view coordinates: the mouse is `ImGui mouse - viewport origin`, overlays (selection outlines, gizmo, tile cursor) draw through `ViewDraw`, which adds the origin and draws into the Scene window's own draw list, and "hovered" replaces `io.WantCaptureMouse` as the test for "the mouse is on the scene". While playing, `SetNextFrameWantCaptureMouse(false)` over the panel lets clicks reach the game.
- **Layout**: `DockLayout.ApplyDefault` builds the default arrangement (Hierarchy left, Scene centre, Inspector and Tiles right, Log/History/Profiler/Engine/Post effects/game panels as tabs at the bottom) by calling the native `igDockBuilder*` functions (ImGui.NET does not wrap them but `cimgui` exports them). It runs when no `imgui.ini` exists or on View > Reset layout. **Order matters (found in the window):** the layout builder and `DockSpaceOverViewport` must run first in the GUI pass (`IEditorShell.BeginFrame`, called before `Hud()` and the game's windows), because windows submitted before the dock space in a frame never dock into it.
- **Assets window** (`AssetBrowserPanel`, `AssetFolder` scans the asset root into a sorted tree of asset names): a prefab dragged onto the Scene panel is instantiated through `EditorHooks.Instantiate`, placed under the mouse (2D: the camera's world point, keeping the prefab's Z; 3D: the mouse ray on the ground plane, else 6 units ahead) and selected, as one undo step (`SceneEditor.Assets.cs`).
- **Play / Pause / Stop** are a toolbar at the top of the Scene panel (and the menu / F3): Play snapshots the scene, the game runs in the panel, Stop restores the snapshot.
- **Limits**: a game code change needs a rebuild and an editor restart (no assembly reload yet); the editor assumes the game's window title and a single scene file; the debug panels of a game (`DebugGui`) are docked by title, so a new game panel floats until its title is added to `DockLayout`; pixel-perfect mode is switched off in the Platformer while editing is not needed any more (the panel is the viewport) but a pixel-perfect game inside the editor has not been tried.

The sections below describe the editor's internals; they were written when the editor was a mode of the game window, and where they say "F2" or "the whole window" the standalone editor replaces that with the always-on editor and the Scene panel above.


F2 toggles `SceneEditor` (internal, owned by `Game`; `Game.IsEditing`). While on: `FrameSystems`, `FixedSystems` and the timestep are frozen exactly as with `IsPaused`, and `RenderClock.Alpha` is forced to 1 (a frozen simulation must draw its real state: a stale fraction would leave moved entities part-way back). The window gets a menu bar (File: Save scene Ctrl+S / Reload / Close; Edit: New, Duplicate Ctrl+D, Delete Del), a `DockSpaceOverViewport` with a pass-through central node (docking is switched on in `GameWindow.OnLoad`), the `HierarchyPanel`, and the inspector's details in its own window (`EntityInspector.DrawDetailsWindow`; the hierarchy and inspector share one selection, `EntityInspector.Selected`).

- **Rendering** (superseded by the scene panel above): the in-window editor let the game draw to the whole window with the editor windows floating over it.
- **Scene view input** (`SceneEditor.Viewport.cs`) reads ImGui's mouse (so `io.WantCaptureMouse` cleanly separates UI from scene): left-click picks, a click on the gizmo starts a drag, middle-drag pans, wheel zooms about the cursor, Ctrl snaps to 8 units. Ctrl is read from `IsKeyDown(LeftCtrl/RightCtrl)`, not `io.KeyCtrl`, which lags a frame behind a quick chord. The selection outline and gizmo are drawn on ImGui's background draw list (over the scene, under the windows).
- **Pure, unit-tested logic**: `EntityPicking` (sprite quad hit test with pivot, scale and rotation; topmost Z, then smaller quad; sprite-less entities hit within 12 screen px; tile layers never picked), `TransformGizmo`/`GizmoApply` (see the 3D view section), `EditorCameraControls` (pan, zoom about a point, clamp), `EntityCloner` (duplicate via the boxed component API; copy is offset, renamed " (copy)", with no render history).
- **What the game provides** (`EditorHooks`, filled from `Game`'s virtual members): `SceneCamera` (null = panels only, no scene view), `ScenePath` (null = Save/Reload disabled) and `SceneReloaded()` (re-find what was cached from the old world, as after a quick-load; the sample's `AfterWorldReplaced`). A game's own update code must stop while `IsEditing` (the sample returns early from `Update` and skips the camera follow).
- **Moving an entity** also clears its `PreviousTransform` (see above), so it is drawn where it is.
- **Undo/redo** (`Editor/Undo`, pure and unit-tested): `CommandStack` (undo list + redo list, capacity 256, a new change clears redo) of `IEditCommand`s (`Do`, `Undo`, `Description`, `Affected`): `SetComponentCommand` (before/after boxed values), `AddComponentCommand`, `RemoveComponentCommand`, `EntityLifetimeCommand` (create or delete, via `EntitySnapshot`). Decisions: (1) commands store a **tracked id** (`EntityTracker`), never an `Entity`, because undoing a delete creates a new entity whose generation differs; the tracker is re-bound to the new handle so older commands about it (a move made before the delete) still resolve; (2) live gestures are recorded once, when they end: the gizmo captures the transform at drag start and `Push`es a `SetComponentCommand` at mouse-up, the inspector remembers the value before the first change of a gesture (`PendingEdit`) and commits when no ImGui item is active any more, so a whole drag or typed name is one step; `Push` records an already-applied change, `Execute` does and records; (3) `EditContext.SetComponent` clears `PreviousTransform` on any Transform write, so undo cannot leave an entity drawn part-way; (4) the history is cleared whenever the editor is toggled and on Reload, because the game runs freely while the editor is off and Reload makes every handle stale; (5) the inspector records only while `EntityInspector.History` is set (editor on), so the F1 debug inspector stays a plain live editor; (6) undo is ignored while a drag or text field is active. Ctrl+Z undoes, Ctrl+Y or Ctrl+Shift+Z redoes, both also in the Edit menu with the step's description; after undo/redo the entity the step touched is selected (or nothing, if it no longer exists).
- **Play / Stop** (F3 or the menu bar button): `Play` takes `Scenes.Save()` as an in-memory snapshot (`EditorHooks.Snapshot`), clears the undo history, and lets the game run for real inside the editor (`Game.IsEditing` is false while playing, `Editing = Active && !Playing`); the hierarchy and inspector stay visible and editable as live tweaks (not undo steps), while File/Edit and the scene view's picking, gizmo and pan/zoom are disabled. `Stop` does `World.Clear()` + `Scenes.Load(snapshot)` + `SceneReloaded()`, clears the history again (every handle is stale) and calls `PlayStopped`; turning the editor off while playing stops first. The game gets `PlayStarted()` / `PlayStopped()` hooks (the sample begins a fresh run both times: new `GameSession`, start point from the hero, fresh door). Decisions: snapshot through the scene serializer rather than a second world, because it already round-trips every registered component and is what Save and quick-save use; the shortcut is F3, not a Ctrl chord, because Ctrl+P also reaches the game while it plays (the sample's pause key); only registered components survive Play/Stop, so unregistered runtime-only data is lost.
- **Tile painting** (`Editor/Tiles`): select a tile layer entity, switch Paint mode on (B or the "Tiles" window checkbox) and the mouse paints the palette tile (left) or erases (right); the cell under the cursor is outlined. `TileCells` (world point to cell given the layer entity position and tile size, cell bounds, Bresenham `Line` so fast drags leave no gaps), `TilePaintStroke` (changes the layer live, remembers each cell original id once) and `PaintTilesCommand` (before/after per cell) are pure and tested; `TilePainter` is the ImGui half (palette drawn from the tile set atlas texture, mouse handling, cursor). A stroke is one undo step, recorded when the button is released and tied to the layer it started on even if the selection changes. Decisions: tile layers are shared **assets**, not entities, so the command holds the `TileLayer` itself and `EditContext.DirtyTileLayers` tracks unsaved ones; Save writes each dirty layer with `TileLayerJson.Write` to `Game.EditableAssetPath(name)` (default: the asset root; the sample points it at the project `Assets/` folder like the scene); layer edits are not rolled back by Reload or Stop (they live in the asset, not the world snapshot), so painting then Play then Stop keeps the paint. Collision: `CollisionSolver.Grid` / `PhysicsSystem.Grid` are settable, and the sample rebuilds its grid from the edited ground layer in `StartFreshRun` (Play and Stop), because physics holds a grid built once at load.
- **Hot-reload with the editor**: saved tile layers are passed to `EditorHooks.AssetWritten` so the watcher does not reload the file the editor just wrote.
- **Known limits**: Save writes the whole live world through `SceneSerializer`; prefab instances are written as prefab + overrides (see Scenes), so a saved level stays lean, but whatever runtime state the simulation had written into components before the editor was opened (animation state, contacts, `PreviousTransform`) is saved too, so open the editor early; the sample saves to `Assets/scenes/level.scene.json` in the project tree when run from a build inside it (the next build copies it to the output folder), else to the copy beside the exe; no rotate/scale gizmos, no multi-select.

- **History window and prefab commands (phase 18)**: `HistoryPanel` lists `CommandStack.UndoCommands`/`RedoCommands`; clicking a row calls `UndoMany`/`RedoMany` to go there. Edit > Save as prefab calls `SceneSerializer.SaveAsPrefab` (writes `SerializeEntity` and adds a `PrefabLink`); Edit > Revert to prefab runs `RevertToPrefabCommand`, which snapshots the components before and after `SceneSerializer.RevertToPrefab` (overwrite prefab components, remove registered ones the prefab lacks) so it is undoable. The prefab logic lives in Scenes because only it can see the registry's serializers; the editor reaches it through `EditorHooks` delegates. Tile painting has rectangle and fill brushes (`TileShapes`, pure and unit-tested) with flip flags (`TileBrush`).
## Projects, the hub and building games (`src/Engine.Editor/Projects`, phases 21-22)

- **A project** is a folder with a `*.csgame.json` file (`ProjectFile`: name, game C# project, compiled game library, launcher project, assets folder, first scene, all relative to the file), an `Assets` folder, a `Game` library project and a `Launcher` project. `Editor.exe <project file>` builds the game (`dotnet build`, skipped with `--no-build`), loads the library from a **shadow copy** (`GameLibrary.ShadowCopy`: Windows will not overwrite a loaded DLL, so the original can be rebuilt while the editor runs) and opens it. `Editor.exe` with no arguments shows the **hub** (`HubShell` on a bare `HubGame`: New project, Open project (native file dialog through `NativeDialogs`), recent projects from `%AppData%\Game Editor\recent.json`); opening builds in the background with the output on screen, then starts a second editor process on the project and closes the hub. The editor is a separate process per project, which also makes "Build and reload game code" simple: build, then restart on the same project (asking to save first).
- **Building is the SDK's job.** `DotnetBuild` runs `dotnet build`/`dotnet publish` and passes `-p:EngineDir=<the editor's folder>`; a project's `Directory.Build.props` turns that into `Reference` items for `Engine.*.dll`, `Silk.NET.*.dll`, `ImGui.NET.dll` and `StbImageSharp.dll`, so a game compiles against exactly the engine the editor runs on (decision: ship the engine DLLs next to the editor instead of NuGet packages; less to maintain now, upgrades are manual). `Directory.Build.props` also holds the same path as a default for building outside the editor; `ProjectTemplate.UpdateEngineDirectory` rewrites it when a project is opened by an editor in another place. The user needs the .NET SDK installed; a missing `dotnet` is reported, not thrown.
- **New projects** come from `ProjectTemplate` (text templates in `ProjectTemplate.Files.cs`, a generated sample sprite through `PngWriter`): `Game/<Name>.Game.csproj` (library, compiles against the engine, content-links `Assets` so the launcher ships them), `<Name>Game.cs` (a `Game` with a camera, sprite batch and the scene loaded; the editor and the launcher run the same class), `<Name>Module.cs`, `Launcher/<Name>.csproj` (exe; copies the engine assemblies, the natives (`cimgui`, `glfw3`, `soft_oal`) next to the program where .NET looks for them, and `game.settings.json`), a first scene and README. `Editor --new <folder> <name>` creates and builds one without a window.
- **Publish** (Project > Publish game, or `Editor --publish <project> [folder]`) is `dotnet publish` of the launcher, self-contained for win-x64, into `Build/win-x64`. **Found by running the published exe:** the natives must sit beside the program (the template copies them to the root); with only a `runtimes` folder .NET never finds `cimgui`. **Validate assets** (`AssetValidator`) loads every recognised file through the game's own loaders and lists failures; scenes load into a scratch world.
- **Player settings**: `GameSettings` (`game.settings.json` next to the program: window size, full screen, vsync, master volume) is read by `GameLaunch.Default`; the editor's `GameLaunch.ForProject` ignores it. **The debug overlay (Engine/Profiler/Log windows) is hidden until F1** for every game; the editor turns it on to show those windows as docked tabs, and the hub hides it again.
- **Look**: `Win11Theme` (called from the window's ImGui setup callback, which runs before the font atlas is built) loads Segoe UI and merges Segoe Fluent Icons (`Icons`), sets the dark Fluent palette with the system-blue accent, rounded corners and roomier padding; `WindowChrome` asks Windows for a dark title bar. ImGui's own settings file is switched off (`DisableLayoutAutoSave`: it saved broken layouts when a process was killed or restarted); the layout is saved only by View > Save layout (`%AppData%\Game Editor\layout.ini`) and the default layout is built when none exists.

## 3D editor view, gizmos and selection (phase 15)

- **3D view** (`SceneEditor.Viewport3D.cs`): a game that overrides `Game.SceneCamera3D` gets an orbit camera in the editor (`Rendering3D/OrbitCamera`: target, distance, yaw, pitch; pure and tested): middle-drag or Alt+left-drag orbits, with Shift pans, the wheel zooms, F frames the selection (`FocusOn` backs off until the bounding sphere fits the field of view). The editor writes the game's `Camera3D` every frame while editing, so a game with its own fly camera must stop applying it and take the view back afterwards (`FlyCamera.CopyFrom`; the sample does this in `Draw`). With both cameras supplied the 3D one wins. **Decision: the scene is still drawn to the whole window** (panels float or dock over it), not into a docked framebuffer viewport or "game view" panel: games size their cameras from `Window.Resized`, and the post-process chain, input and every cached screen size assume the full window, so a viewport panel needs a viewport abstraction in `Game` (size events, mouse offset) that touches every game. Revisit if a second view (editor camera plus game camera side by side) is wanted.
- **3D picking** (`EntityPicking3D`, pure): the mouse ray (`Camera3D.ScreenPointToRay`) against each drawn mesh's bounding box moved into the box's own space by the inverse world matrix (so a rotated or scaled crate is hit where the crate is; the direction is not renormalised, so distances stay in world units), nearest hit wins; entities with no box (lights, markers) are hit within 12 screen px (`WorldUnitsPerPixel` keeps that constant on screen). Boxes come from a `BoxSource` delegate (`RenderedBoxes` in Runtime resolves `MeshRenderer` meshes and `ModelRenderer` parts through the assets), which keeps the maths free of GL and assets. Triangle-accurate picking is not done: boxes are coarser but fast and forgiving.
- **Gizmo** (`Editor/Gizmos`): `TransformGizmo` does hit testing and drag maths, draws nothing and touches no entity. `IGizmoView` abstracts the camera (`OrthographicGizmoView` over `Camera2D`, `PerspectiveGizmoView` over `Camera3D`: screen ray, projection, world size of a pixel), so one gizmo serves both views; in the 2D view only X, Y and the Z rotation ring exist. Modes (W/E/R): translate (arrows, plus a square that moves in the plane facing the camera), rotate (a ring per axis), scale (stalks with cubes on the entity's own axes, plus a centre cube for uniform scale). Space (X): world or local axes for translate and rotate; scale is always local, because scale lives on the entity's axes. Handles are measured in screen pixels, so they keep their size at any zoom or distance, and the nearest handle wins where they overlap. Axis drags use the point of the axis line closest to the mouse ray (`GizmoMath.TryClosestOnAxis`), so the grabbed point stays under the mouse; a ray parallel to the axis is detected and gives no movement instead of a wild one. Rotation is the angle the mouse sweeps around the ring's plane; scale is a ratio of distances (clamped at 0.01). Ctrl snaps the **change** (8 units in 2D, 0.5 in 3D, 15 degrees, 0.1), not the final position, so an off-grid entity keeps its offset.
- **Drag result is a world-space `GizmoDelta`** (translation, a turn about a world axis through the pivot, per-axis scale factors), applied by `GizmoApply` to each entity from the transform it had when the drag began (never from the previous frame, so no drift), converting back through the parent for children (position through the inverse parent matrix, rotation by removing the parent's). One gesture is one undo step: a `SetComponentCommand` per entity, grouped in a `CompositeCommand` when several moved. This replaced the 2D-only `MoveGizmo`.
- **Multi-select** (`EditorSelection`, owned by the inspector; `EntityInspector.Selected` is its primary and setting it selects only that entity): Ctrl+click in the scene or the hierarchy toggles; the inspector shows the primary; the gizmo stands at the average position of the selected entities that have no selected ancestor (`GetTopLevel`, so a parent and its child are not moved twice) with the primary's orientation, and a rotation swings positions round that pivot; duplicate and delete act on every top-level selected entity (with subtrees) as one undo step; every selected entity is outlined (the primary brighter). Scale multiplies each entity's own scale (positions are not scaled about the pivot).

## 3D rendering (`src/Engine.Rendering3D`)

- **Pipeline per frame** (`MeshRenderSystem`, a render system added before the 2D passes; partial files `.Items`, `.Draw`, `.Shadows`, `.Lights`): gather lights; clear the depth buffer; fit the sun's shadow view and **gather a draw list** (`DrawItem`s) from `MeshRenderer` entities and `ModelRenderer` parts, frustum-culled by bounding sphere (casters are collected separately and not culled by the camera); sort; render the **shadow map**; then the main pass: opaque and cut-out items grouped by material then mesh, runs of the same mesh and material as **one instanced call**, then **blended** items farthest first with depth writes off; depth test and culling are switched off afterwards so sprites, tiles and the HUD drawn later land on top. Entities with a `PreviousTransform` (or a `Parent`) are drawn interpolated through `TransformHierarchy`. Stats: `DrawnLastFrame` (meshes), `DrawCallsLastFrame`, `CulledLastFrame`.
- **Depth buffer**: the window asks for 24 depth bits (`GameWindow`), and `RenderTarget` has an optional depth renderbuffer; `PostProcessChain` gives only its scene target (target 0) one, because that is where the scene is drawn when an effect is on. Verified in the window with the vignette on and off.
- **Conventions and decisions**: (1) `Projection3D.Perspective` and `Projection3D.Orthographic` are written for OpenGL's clip depth (-1..1): `Matrix4x4.CreatePerspectiveFieldOfView` targets Direct3D (0..1), which would leave the near plane inside the volume and halve depth precision. (2) Matrices reach the shader row by row, so a row-vector `Matrix4x4` arrives as the transposed matrix GL expects and the shader multiplies `matrix * vector`. (3) The normal matrix is the inverse transpose of the model matrix (`ModelMatrix.NormalMatrix`), so non-uniform scale does not skew lighting. (4) Lighting is in linear light: base colour, texture and emission are decoded with gamma 2.2, lit, then re-encoded. (5) One `DirectionalLight` (the first found; it shines along the entity's forward -Z) and any number of `PointLight3D` (smooth falloff `(1 - (d/r)^2)^2`, zero at the radius); the shader takes at most 8 per draw and the CPU chooses the best ones per mesh. Lights are components, so scenes save them and the inspector edits them. (6) Meshes are procedural (`MeshBuilder`: cube, plane, sphere, capsule) added to `Assets` by the game under the names its scene files use, or come from glTF. (7) `Texture2D` has `TextureFilter.Trilinear` (mipmaps) and `SetRepeat()` because 3D surfaces tile and are seen at grazing angles.
- **Materials and shading (phase 17)**: `Material` is a shared **metallic-roughness (PBR)** asset: base colour (+ texture), `Metallic`, `Roughness`, optional metallic-roughness map (green = roughness, blue = metallic, linear), tangent-space normal map with `NormalScale`, `Emissive`, `AlphaMode` (Opaque, Mask with `AlphaCutoff`, Blend), `Unlit`, `DoubleSided`, `CastShadows`; loaded from `.material.json` by `MaterialLoader` (`MaterialJson` is strict: an unknown key throws, and the old `shininess`/`specular` say to use `roughness`/`metallic`). Decision: **replace Blinn-Phong instead of keeping both**, because glTF already carries metallic-roughness, one shading model is less code and every material then means the same thing in any file. The fragment shader is Cook-Torrance (GGX distribution, Smith-Schlick geometry, Schlick Fresnel), Lambert diffuse reduced by metalness and Fresnel; lights are plain colour times intensity (the usual 1/pi is folded into them, so a light looks as bright as it did under simple shading). **No environment map**, so metals would be black without lights: `Lighting3D` gives a two-colour sky/ground (`ReflectedSky`, `ReflectedGround`, `ReflectionStrength`) that shiny surfaces reflect (rough ones average it), which is a cheap stand-in for image-based lighting. `Vertex3D` gained a tangent (48 bytes); `MeshData` generates tangents from the UVs when a builder supplies none (`TangentGenerator`: per-triangle U direction, Gram-Schmidt against the normal, handedness from the UV mirroring; V is flipped because a normal map's green channel points up the image).
- **Instancing and sorting**: model matrix and normal matrix are **per-instance vertex attributes** (locations 4-10, `InstanceBuffer`, one shared growing buffer attached to the mesh's VAO just before each draw), so a single draw is an instanced draw of one and the shader has no model uniform. Opaque items are sorted by identity hashes of material then mesh (a hash collision only costs batching). A run is instanced only when all point lights fit the shader's 8 at once (otherwise their per-mesh selection would differ between the instances of a run, so items are drawn singly with their nearest lights); skinned items are never instanced (each has its own pose). Blended items are sorted by squared distance of the bounding-sphere centre and drawn singly; sorting per object, not per triangle, so interpenetrating or concave transparent meshes can still sort wrongly.
- **Sun shadows** (`ShadowMap`, `ShadowMath`, `MeshRenderSystem.Shadows.cs`): a 2048 depth texture (constructor parameter) rendered from the sun with an orthographic view fitted to the **bounding sphere** of the camera frustum slice up to `Lighting3D.ShadowDistance` (50), with the centre snapped to whole texels in the sun's view, so shadows neither change texel size when the camera turns nor crawl when it moves; the depth range reaches `casterRange` (120 m) towards the sun so tall things outside the view still cast. The main shader compares with a `sampler2DShadow` (hardware PCF) over a 3x3 grid; bias grows on surfaces facing away from the sun (`Lighting3D.ShadowBias`), plus `glPolygonOffset` in the depth pass. Casters: opaque and cut-out materials with `CastShadows`; cut-out materials discard in the depth pass so a leaf casts a leaf-shaped shadow; blended ones never cast. The pass saves and restores the current framebuffer and viewport (so it works with the post-processing target bound). Limits: one map (no cascades, so a long view trades sharpness for range), the sun only (point lights cast none), no soft penumbra by distance.
- **glTF models** (`Rendering3D/Gltf`, 13c, extended in 14 and 17): `GltfContainer` opens .gltf (JSON) or .glb (12-byte header, JSON chunk, BIN chunk, 4-byte padded), `GltfFile` is the typed subset of the schema (property names as in the spec), `GltfBuffers` resolves data URIs, files next to the model and the glb chunk, `GltfAccessors` reads typed, strided accessors as packed floats or uint indices (integer types, normalised ints, interleaved views, MAT4 for inverse binds; sparse accessors are rejected), and `GltfImporter` (partial: `.Animation.cs` for skins and animations) walks the scene's node tree and returns `ModelData`. Pure and unit-tested. `Model` (GPU asset: meshes, materials and the images embedded in the file, all owned and disposed by the model) is built from `ModelData` by `ModelLoader` (registered by `Game` for `Assets.Load<Model>`), and `ModelRenderer` (component, handle saved as the file name) makes `MeshRenderSystem` draw every part. Decisions: (1) the node tree is **flattened at import** into parts with baked matrices (one matrix multiply per part when drawing) and also kept in `ModelData.Nodes`/`Model.Nodes` (name, parent index, local matrix, parents before children); `ModelPart.Node` names each part's node. Entities are not made per node: a model is one entity drawn by `ModelRenderer`, which keeps instances cheap. (2) glTF and the engine already agree on handedness, Y up, counter-clockwise front faces and texture row 0 at the top, so no flipping; a node `matrix` is column-major for column vectors, which read straight into `Matrix4x4` fields is exactly our row-vector matrix. (3) Fail loudly: `extensionsRequired`, sparse accessors, primitive modes other than triangles, out-of-range indices, skins with more than 64 joints, bad animation data and missing files throw `InvalidOperationException`/`FileNotFoundException` with the glTF index in the message; cameras, lights and morph-target animation are silently ignored (nothing would draw wrongly). (4) Missing normals are generated (`NormalGenerator.Smooth`, area weighted); missing UVs are zero; tangents are generated from the UVs (a file's TANGENT attribute is not read). (5) The material maps straight onto the PBR `Material` (factors, base colour, metallic-roughness and normal maps, emissive factor, alpha mode and cut-off); occlusion maps and emissive textures are not read. (6) Images are decoded by `Texture2D.FromImageBytes` (trilinear, repeat) in `Model`, not the importer, so the importer needs no GL; a model's textures are owned by its `Material.Owned*Texture`, not registered in `Assets`, so reloading a model cannot collide with names. (7) `GltfWriter` writes pieces as a .glb (used by `tools/make-models.cs` for the sample house); `tools/make-arm.cs` writes a skinned, animated arm by hand.
- **Animation and skinning (phase 17)**: the importer reads skins (`ModelSkinData`: joint nodes + inverse bind matrices), per-vertex `JOINTS_0`/`WEIGHTS_0` (`SkinVertex`, a second vertex stream, attributes 11-12; weights are normalised) and animations (`ModelAnimationData` channels of translation, rotation or scale keyframes with linear, step or cubic-spline interpolation; `AnimationSampling` is pure and tested). `ModelAnimator` (component: clip name, time, speed, loop, playing; saved in scenes) is advanced by `ModelAnimationSystem` (a frame system, so a paused game or the frozen editor stops it) into an `AnimatedPose` per entity (kept in the `ModelPoses` cache shared with `MeshRenderSystem`, because components cannot hold arrays): every node starts at its rest transform, channels replace translation/rotation/scale, `ModelPose.ComputeWorld` builds model-space matrices and each skin's **joint matrices** (`inverseBind * jointWorld`, row-vector). Skinned parts are drawn with the entity matrix only (their vertices are already in model space, the joints place them) through a `uJoints[64]` uniform array and the blend of four joint matrices in the vertex shader (the shadow pass skins too); unskinned parts follow their animated node. Decisions: GPU skinning with a uniform array (64 joints) rather than a texture or CPU skinning, because it is the simplest thing that works for characters and keeps the vertex data static; skinned meshes are never frustum-culled (a pose moves them away from their bind-pose bounds) and never instanced. Limits: no blending between clips, no animation events, no morph targets, one clip per animator.
- **Not yet**: cascaded shadow maps and point-light shadows, image-based lighting and a skybox, occlusion and emissive maps, order-independent transparency, GPU instancing of skinned meshes, blending between animation clips, a 3D editor gizmo for lights and colliders.

## 3D physics (`src/Engine.Physics3D`)

**Decision: write our own, in a module of its own, and grow it in stages; do not integrate a library (BepuPhysics, Jolt, PhysX).** Reasons: (1) the project exists to learn how engines work and every other core system (ECS, 2D physics, renderer, editor) is written from scratch with libraries only for plumbing; physics is core, not plumbing. (2) Games here are small (a platformer first); a character-style solver covers most of what is needed and a full rigid-body engine would be the largest single piece of code in the repo for a feature nothing uses yet. (3) The 2D module proved the shape of the solution (swept AABB, per-axis resolution, contact flags, solids as tagged entities), and it extends to 3D by adding one axis, so the first slice is a few hundred lines. (4) The cost is accepted knowingly: no stacking, no joints, no convex/mesh colliders until written. If a game ever needs real rigid-body behaviour sooner than the staged plan delivers it, integrating a library behind the same components (`BoxCollider3D`, `PhysicsBody3D`) is the escape hatch, and the module boundary (physics never references rendering) keeps that swap local. Same dependency rule as 2D: Physics3D references Core only (it uses `Engine.Core.Ray`, which moved to Core so picking and physics share it).

- **Stage 1, built (13d; extended by stage 2)**: dynamic `PhysicsBody3D` + `BoxCollider3D` against `StaticSolid3D` boxes. `PhysicsSystem3D` per fixed step: gather static boxes (brute force), apply gravity (default -9.81 m/s^2, terminal speed 50) and, while the last step ended grounded, a constant ground friction on the horizontal speed (`PhysicsSettings3D.GroundFriction`, 12 m/s^2; reaching zero never reverses the motion), then sweep **X, Z, then Y** (horizontal first, so a landing is judged after sideways motion has settled) with `CollisionSolver3D.Sweep`: the nearest obstacle face ahead of the leading face across the box's extent on the other two axes (shrunk by 0.001 so touching is not overlapping), obstacles behind the leading face ignored (so a body inside a solid can leave it, and one spawned inside passes through), no tunnelling at any speed. Blocked velocity components are zeroed; contacts are probed with a 0.01 skin in six directions and held while resting. `CollisionSolver3D.Raycast` (slab test from `Ray.IntersectsBox`, face normal from the axis the hit point is furthest out relative to the half-size) and `PhysicsSystem3D.Raycast` (also returns the entity that owns the box) answer picking and line-of-sight questions.
- **Stage 2, built (phase 16)**: (a) **Body-vs-body**: every body's box is in `CollisionSolver3D.DynamicBoxes`; a body is swept against static solids and the other bodies, and bodies are stepped lowest first (bottom of the box, ties by entity id) so a stack settles from the bottom up. Hitting a body is a **perfectly inelastic collision along the axis** (`ShareMomentum`): both leave with the mass-weighted average velocity (`PhysicsBody3D.Mass`, 0 or less counts as 1, so older data works), only when closing; the mover stays blocked for the step. Decision: inelastic momentum sharing instead of impulses with restitution, because crates should shove and stop, not bounce, and it needs no solver iterations; limits: a body on top of a moving one does not ride it (only friction-free resting contact), and there are no rotations, so crates never topple. Contacts count bodies as surfaces. Rays hit bodies too. (b) **Capsules and spheres** (`CapsuleCollider3D`; a sphere is `Sphere(r)`, a capsule exactly as tall as wide): **collide and slide**, not a swept box: move (in substeps of at most half a radius, so a fast capsule cannot skip a thin wall), then push out of every overlapping solid along the shortest way (`CapsuleCollision.TryPenetration`: the capsule's axis segment against a box, closed form for the usual upright case, a ternary search for a tilted one, face-exit when the axis is inside), removing the velocity part that points into the surface so it slides along walls and over seams; contacts by testing a hair larger (the contact normal says which side). Other bodies see a capsule as its bounding box, and a capsule treats a body as that body's box, so capsule-vs-capsule is the approximation. (c) **`CharacterController3D`** + `CharacterControllerSystem3D` (before physics): intent (`Move` in world X/Z, a latched `JumpPressed`) becomes acceleration towards `MoveSpeed` (ground and air rates), jumps with coyote time and a jump buffer; ground friction is skipped for controlled bodies because the controller brakes itself. No stepping up ledges, no slope limit. (d) **Oriented boxes**: `BoxCollider3D.Oriented` on a `StaticSolid3D` takes the entity's world rotation (`Obb3`); capsules collide exactly (moved into the box's local space, where it is an ordinary box), box bodies are **pushed out after their move** with the separating-axis test (`Sat.TryPenetration`: 15 axes, face axes preferred, minimum-overlap axis is the way out), so they slide down ramps; rays hit them exactly. Decision: discrete SAT push-out for box bodies, not a swept test: sweeping an AABB against a rotated box needs a different algorithm per feature pair, and ramps are the use case; cost: a very fast box can tunnel a thin oriented solid (capsules substep, boxes do not). A moving body with an oriented collider throws (bodies do not rotate).
- **Not yet**: rigid-body rotation and inertia (topple, roll), mesh and convex colliders, joints, a spatial hash or BVH once static counts justify it, one-way surfaces, stepping up small ledges and a slope limit for the character, capsule-vs-capsule exactness, sleeping.
- **In the sample** (`samples/Scene3D`): Space throws a crate (prefab with `PhysicsBody3D`) that falls, slides to a stop, rests on the floor and stacks and is pushed; the arrow keys walk a blue capsule player (Enter jumps) up a tilted oriented ramp and into crates; a left click casts a ray from the cursor through `Camera3D.ScreenPointToRay`, moves a marker to the hit point and logs the entity, distance and face normal.

## Render interpolation

Fixed steps and display frames do not line up, so drawing the raw simulated position makes motion judder. Entities with a `PreviousTransform` are drawn at `Lerp(previous, current, alpha)` (`PreviousTransform.Interpolate`; scale is not blended). Decisions and reasons: (1) it is an opt-in component rather than a second copy of every `Transform`, so static entities pay nothing; (2) `default` means "no history", so a spawn, respawn or scene load draws at the real position instead of sweeping in from the origin; (3) `RenderClock` (set by `Game` before `Draw`) is handed to the render systems by constructor, not read from a global, and the parameter is optional so systems without it draw the raw state; (4) the camera follow runs in `Game.Draw` (after the steps, with the current alpha) on the interpolated hero position, otherwise it chases a position the sprite is not drawn at and jitters; (5) `LightingEffect` interpolates lights the same way so the lantern stays on the hero.

## Transform hierarchy (`src/Engine.Core/Hierarchy`, phase 14)

- **Model**: `Parent { Entity Value }` makes an entity a child, and then its `Transform` is **local** (relative to the parent); an entity without `Parent` has a world-space `Transform` exactly as before, so flat scenes, physics and every older system are untouched. World placement = `local * parentWorld` (row vectors), computed by `TransformHierarchy` (`GetWorldMatrix`, `GetWorldTransform`, `GetWorldPosition`, `ToLocal`, `GetRenderTransform`/`GetRenderMatrix`). Edits go through `SetParent` (refuses a parent that is the child or below it; `keepWorld: true` rewrites the local transform so the entity stays put, which is what dragging in the editor wants) and `Destroy` (the subtree); `GetChildren`/`GetSubtree` scan the `Parent` pool and are for tools.
- **Decisions and reasons**: (1) **no cached world matrices**: a walk up the chain (one component lookup per ancestor, one for a root) instead of a hierarchy system that writes a `WorldTransform`, so there is nothing to go stale when a parent moves mid-frame, in the editor, or after undo; the cost is paid per drawn entity, and a root pays a single `Has<Parent>`. A cached matrix is the next step if profiling shows deep trees. (2) **Transform stays one component** and its meaning depends on `Parent`, rather than splitting into `LocalTransform` + `Transform`: forty files read `Transform` as world space, and most entities never get a parent. (3) **Render interpolation blends every level** (`GetRenderMatrix` interpolates each ancestor with a `PreviousTransform`), so a child follows a moving parent smoothly; a root keeps the old fast path. (4) **`Parent` holds an `Entity`, so it is not a registered component**; scenes store `"parent": <index of another entry in the same file>` on the entry, validated before anything is created (range, self, loops), and the link is added after all entities exist, so a child may come before its parent in the file. A dead parent counts as no parent. (5) **Physics**: static solids (`StaticSolid`/`StaticSolid3D`) may be children and use their world position; a moving body (`PhysicsBody`, `PhysicsBody3D`) must be a root and the systems throw otherwise (a body is moved in world space and fixing that needs a world-to-local write-back that nothing needs yet). Tile layers are roots too. (6) Shear (a rotated parent with a non-uniform scale) cannot be expressed as position/rotation/scale: `Transform.FromMatrix` returns the closest, which is only what sprites and lights read; meshes use the full matrix.
- **Editor**: the Hierarchy window is a tree (drag onto an entity to reparent, drop on the strip at the bottom to unparent, "+ Child", a filter flattens it). `ReparentCommand` stores old/new parent by tracked id and old/new local transform (undo restores the exact values); deleting or duplicating an entity does its whole subtree as one `CompositeCommand` of `EntityLifetimeCommand`s (children are deleted first and recreated after their parent, so `EntitySnapshot` can re-link through the tracker); the gizmo and picking work in world space and convert to local on write (`MoveSelected`).

## ECS (`src/Engine.Core/Ecs`)

- `Entity` = (Id, Generation); generation 0 is `Entity.Null`. `EntityAllocator` hands out ids and bumps generations on destroy so stale handles fail `IsAlive`.
- `World` (partial: `World.cs` lifetime, `.Components.cs`, `.Queries.cs`, `.Internals.cs`) owns one `ComponentPool<T>` per component type, stored in a `Dictionary<Type, IComponentPool>`.
- `ComponentPool<T>` is a sparse set: `_sparse[entityId] = denseIndex + 1`, packed `Dense`/`Components` arrays, swap-remove.
- Queries (`Query<T1>`, `<T1,T2>`, `<T1,T2,T3>`) pass components by `ref`; they take an iteration lock so `Create/Destroy/Add/Remove` throw mid-query. Use `CommandBuffer` to defer, `Set` to overwrite existing components safely.
- Systems implement `ISystem.Update(World, double dt)`; `SystemGroup` runs them in insertion order. `Game` exposes three groups: `FixedSystems`, `FrameSystems`, `RenderSystems`.

## Physics (`src/Engine.Physics2D`)

- **Per fixed step** (`PhysicsSystem`): for each `Transform`+`PhysicsBody`+`BoxCollider`: apply gravity (`PhysicsSettings.Gravity`, `GravityScale`, clamp to `MaxFallSpeed`), sweep X then Y with `CollisionSolver.Sweep` (zero the blocked velocity component, snap to the face), then probe a 0.01 skin in four directions to set `PhysicsBody.Contacts` (so contacts persist while resting against a surface, even with zero velocity or zero gravity).
- **Solids**: `TileGrid` (cell (0,0) bottom-left, outside = empty) plus `StaticSolid`-tagged `BoxCollider` entities gathered each step (brute-force list; a spatial hash is deferred until static box counts justify it).
- **Sweep algorithm**: per axis, find the nearest obstacle face ahead of the leading edge across the box's extent on the other axis (shrunk by `Epsilon` = 0.001 so touching is not overlapping); obstacles already behind the leading edge are ignored, so overlapping a solid lets a body leave it but also lets a body spawned inside pass through. Tunnelling-proof for any speed.
- **Platformer controller**: input layer writes `PlatformerIntent` per frame (`MoveX`, `JumpHeld`, sticky `JumpPressedPending`); fixed-step `PlatformerControllerSystem` (before `PhysicsSystem`) converts the pending flag to a jump buffer, tracks coyote time from last step's `Below` contact, accelerates toward target speed (ground/air), jumps when buffer and coyote are both positive, cuts the jump when released early, and raises gravity scale while falling. Tuning (`PlatformerTuning`) and timers live in one `PlatformerController` component (the ECS supports queries of up to 3 components).
- **Moving platforms**: `MovingPlatform` (path `Travel`, `Speed`, runtime `Distance`/`Returning`, `default` is valid) on an entity with `BoxCollider` + `StaticSolid`; `MovingPlatformSystem` (fixed, first after `PreviousTransformSystem`) advances it with `MovingPlatformMath.Advance` (ping-pong, reflecting overshoot) and shifts riders by the same delta. A rider = grounded body whose feet are at the platform's old top with horizontal overlap. A platform rising into a body that was at/just above its top lifts it to the new top (otherwise the body ends up inside the solid and, per the sweep rules, falls through). Decisions: platforms stay `StaticSolid`s so `PhysicsSystem` needs no change; riders are shifted, not swept, so a platform can carry a rider into a wall and does not push bodies it hits from the side or above (place paths in open space); the path start is the entity's placed position, so scenes only set travel and speed.
- **Not yet**: one-way platforms, slopes, body-vs-body collision, depenetration, pushing/crushing by moving platforms.

## Tilemaps (`src/Engine.Tilemaps`)

- `TileLayer` stores tile ids in a `Dictionary<long, TileChunk>` of 16x16 chunks keyed by packed chunk coordinates; chunks appear when a tile is placed and vanish when empty. Cell (0,0) is bottom-left, Y up, negatives allowed (`cell >> 4` and `& 15` floor correctly). The renderer reads chunks through `TryGetChunkTiles` (a `ReadOnlySpan<int>`, no copies).
- `TileSet` = atlas texture handle + tile size/columns/rows/spacing/margin; ids are 1-based, row-major; per-tile `IsSolid`.
- Layers and tile sets are **assets** (`Assets.Add("layer/ground", layer)`), referenced from the `TileLayerRenderer` component by handle. The layer entity's `Transform` position is the world position of cell (0,0); its Z is draw depth. `TileLayer.TileSize` is world units per tile (art is 16 px drawn at 32).
- `TileLayerRenderSystem` collects layers for its pass (`foreground` flag), sorts by Z, asks `Camera2D.GetVisibleBounds` for the visible world box, converts to a chunk range, and submits one `SpriteDraw` per visible tile to the shared `SpriteBatch` (UV rect inset by 0.02 px to stop atlas bleeding). Cached per-chunk GPU meshes are a later optimisation.
- `TileGridBuilder.FromLayer(layer, tileSet, layerOrigin)` makes the physics `TileGrid` from the layer's used bounds and the tile set's solid flags.
- **Cached chunk meshes (phase 20)**: `TileLayerRenderSystem` draws each visible chunk from a GPU mesh built once (`TileChunkMeshBuilder` makes the quads in layer space, white; `TileChunkMesh` uploads them; `TileMeshCache` keeps them per layer and chunk). The layer's origin (parallax and pixel snapping included) goes in as the `uOffset` uniform and its tint as `uTint`, so scrolling or fading never rebuilds anything. A chunk is rebuilt when `TileChunk.Version` (bumped by `SetTile` when a value really changes), `TileSet.Version` (a new animation) or the atlas size changes; chunks not drawn for 240 frames are freed. Animated tiles are left out of the mesh and drawn through the sprite batch with their current frame. The system owns GPU buffers, so it is `IDisposable` and `Game` disposes every disposable system on close. `SpriteBatch.Gl` and `CountExternal` let a render system issue its own draws and keep the stats honest.
- **Tile flags, animation and parallax (phase 18)**: a stored tile value is `TileId`: low 28 bits the 1-based tile, bits 28-30 flip horizontal/vertical/diagonal (same layout as Tiled, so import copies bits). `TileSet.IsSolid`/`GetSourceRect` mask the flags, and the render system turns them into `SpriteFlip` (the diagonal flip transposes the UVs in `SpriteQuad`). Animated tiles live on the tile set (`SetAnimation(tile, frames)`, saved in `TileSetData.Animations`); `TileLayerRenderSystem` keeps one clock and calls `ResolveFrame`, so every animated tile of a set animates in step. `TileLayerRenderer.Parallax` (0 = moves with the world, 1 = fixed to the camera) shifts the layer by a fraction of the camera position; collision never uses a parallax layer.
- **Tiled import (phase 18)**: `TiledReader` parses `.tmj`/`.tsj` (JSON, finite maps, embedded or external tile sets) into plain records; `TiledConverter` is pure: flips Y, splits a Tiled layer per tile set (an engine layer draws one atlas), moves flip bits into `TileId`, reads a boolean `solid` tile property, converts animations and objects (world units via `WorldUnitsPerPixel`); `TiledSpawner` loads textures, registers tile sets and layers as assets and creates one entity per layer. Objects stay in the `ImportedMap` because what they mean is the game's. Decision: no `.tmx` (XML) and no infinite maps yet; JSON is what Tiled exports and the engine already parses.

## Animation (`src/Engine.Animation`)

- `AnimationClip` = pixel rects + fps + `AnimationLoopMode` (Loop/Once/PingPong); `GetFrameIndex(time, out finished)` is pure.
- `AnimationStateMachine` (shared asset): float parameters (booleans are 0/1), states (each a clip), and ordered transitions (`From` a state or any, `To`, conditions on parameters, optional `RequiresFinished`). First matching transition wins; any-state transitions never target the current state. One transition per update.
- `SpriteAnimator` component = machine handle, current state, state time, speed, finished flag, parameter array (create with `SpriteAnimator.Create`). `AnimationSystem` (frame group) advances time, evaluates transitions, writes `Sprite.Source`. Game systems write parameters first (sample: `HeroAnimationSystem` from `PhysicsBody`).

## Scenes and prefabs (`src/Engine.Scenes`)

- **File shapes** (camelCase, indented). Scene: `{ "version": 1, "entities": [ { "prefab": "optional.prefab.json", "parent": 0, "components": { "Transform": { "position": { "x": 1 } } } } ] }` (`parent` is the index of another entry; see the Transform hierarchy section). A prefab file is the same entity shape (and may itself name a `prefab`, depth limit 16). Asset data files: `.layer.json` (rows of tile ids, top row first, plus `originX/originY` of the bottom-left cell), `.tileset.json` (texture name, tile size, solid ids), `.anim.json` (parameters, states with `grid` or `frames` clips, transitions with conditions by name).
- **Components**: `ComponentRegistry.Register<T>(name)` builds a `TypedComponentSerializer<T>` (System.Text.Json with `IncludeFields`, camelCase, enums as text, computed read-only properties skipped). Only registered components are saved; unknown names in files throw naming the component. Names are stable file names, independent of the C# type. `Runtime.EngineComponents.RegisterAll` registers the engine's ten; games add their own (sample: `Patrol`).
- **Assets by name**: `AssetHandleConverter<T>` writes `assets.NameOf(handle)` (or `null`) and reads via `assets.Load<T>(name)`, which returns cached/in-memory assets first and otherwise loads the file. So anything a scene refers to needs a registered `IAssetLoader<T>`.
- **Load is two-phase**: resolve prefab chains and parse every component into a ready-to-apply action first (errors surface here, world untouched), then create entities. Prefab override = `JsonMerge.Apply` (RFC 7386: objects merge recursively, arrays/scalars replace, `null` removes). Prefabs are cached assets; resolution works on `DeepClone`d copies so cached templates are never mutated.
- **Save** writes every entity in id order with its registered components (`SerializeEntity` returns a valid prefab body). Quick-save in the sample writes `saves/quicksave.scene.json` next to the exe; quick-load does `World.Clear()` then `LoadFile`.
- **Prefab links**: an entity created from a prefab (scene entry or `Instantiate`) gets a `PrefabLink { Prefab }` component (owned by Scenes, deliberately **not** registered, so it is never written as a component). `Save()` writes such an entity as `{ "prefab": name, "components": <only what differs> }`: the base is the prefab built in a scratch world and written through the same serializers (so equal values format alike), and `JsonMerge.Diff(base, current)` is the inverse of the merge patch (changed fields, whole arrays, `null` for a removed component or field; numbers compare by value). An unchanged instance is just `{ "prefab": name }`, and a saved instance keeps following later edits to its prefab for every field it did not override. `SerializeEntity` (the public one-entity method) still writes everything, because its job is authoring a new prefab. Cost: Save builds each distinct prefab once per call.
- **Limits**: no `Entity` references between components (not remapped), no scene-in-scene, an instance cannot be re-pointed to another prefab except by editing `PrefabLink`, a prefab file edited on disk is not picked up until the asset is reloaded (no hot-reload yet), no editor yet.

## Diagnostics and tools (`Engine.Core/Diagnostics`, `Engine.Core/Logging`, `Engine.Runtime/Inspector`)

- **Logging**: `Logger` (Core, no Silk.NET) filters by `MinimumLevel` (default Info) and fans each `LogEntry` (time, level, category, message) out to its `ILogSink`s; sink exceptions propagate (fail loudly). `Game.Log` is created with a `ConsoleLogSink` and a 500-entry `MemoryLogSink` (ring buffer, so memory stays constant) that feeds `LogPanel`. Decision: an instance owned by `Game` rather than a static `Log` class, so tests and tools can build their own loggers and sinks, and a file or editor sink is one `AddSink` away. The clock is injectable for exact timestamps in tests.

- **Profiler**: sections are registered once by name and timed by integer id (`Begin()` returns a tick count, `End(section, start)` adds to that frame's total). `BeginFrame()` rolls the totals into a 120-frame ring buffer per section. Sections that run several times per frame (fixed systems on a multi-step frame) sum. The clock is injected (`Func<long>` plus ticks per second) so tests use exact values. `SystemGroup.Profile(profiler, "Fixed")` resolves a `group/SystemType` section per system up front, so a profiled run allocates nothing. `Game` calls `BeginFrame()` at the start of `OnUpdate` and closes the `CPU frame` section at the end of `OnGui` (the last callback of a frame, so it also works with the overlay hidden; it excludes the vsync wait in the buffer swap).
- **Type-erased component access** (`World.Reflection.cs`): `GetComponentTypes`, `GetBoxed`, `SetBoxed`, `AddBoxed`, `Remove(entity, Type)` (pools gained `ComponentType`/`GetBoxed`/`SetBoxed`/`AddDefault`). They box and allocate, so they are for tools only. Structural ones respect the query lock; `SetBoxed`, like `Set`, is allowed mid-query.
- **Inspector**: `ComponentRegistry.Describe()` supplies name, type and a valid default value (`Register<T>(name, defaultValue)`, e.g. `Transform.Identity`) for the Add menu. `FieldEditor` draws one widget per type (boxed `object` in, changed flag out) and recurses into structs: public-field structs are edited in place on the box, positional record structs (`Rect`, `Color`) are edited per constructor parameter and rebuilt through the constructor. Quaternions go through `QuaternionMath` (Euler degrees, pitch clamped at +-90). The inspector copies the component out, edits, and writes back only when something changed.
- **Audio flow**: `Game.OnLoad` registers `AudioClipLoader` and creates the device with `OpenAlAudioDevice.TryCreate` (a missing OpenAL library or output device yields a `NullAudioDevice` whose `Description` explains why; the overlay shows it). `OnUpdate` calls `Audio.Update()` (frees finished voices). `OnClosing` disposes the device after `Unload` and before `Assets`. `Play` takes a free voice or steals the oldest (`VoicePool`), buffers upload on first play or `Preload`, and handles are generation-checked so a stale `VoiceId` never stops someone else's sound.
- **Audio depth (phase 19)**: `IAudioDevice.Mixer` is a tree of `AudioGroup`s (pure data: volume, mute, `EffectiveVolume` = product up the parent chain); each voice remembers its own volume and group, and `Update()` re-applies the gain when either changed, so group changes follow sounds that are already playing. Positioned sounds (`PlayAt`) are OpenAL sources with the inverse-distance-clamped model; unpositioned ones are `SourceRelative` at the origin with rolloff 0, so the listener never affects them. `Spatialization.Attenuation` is the same formula in C# for gameplay code and tests. Streams (`PlayStream`) take one voice, queue 4 buffers of 32 KiB and refill them in `Update()`; looping rewinds the stream rather than using AL looping; the device owns and disposes the stream. `AudioSourceSystem` (frame group) is the data-driven path: it starts `AudioSource` entities, keeps positioned ones at their entity (2D sources take the listener's Z, so draw order is not distance), stops sounds of dead entities, and places the listener from the `AudioListener` entity. Runtime state (voice per entity) lives in the system, not the component, so scenes stay clean. **Decision:** OpenAL contexts are process-global (`MakeContextCurrent`), so every test class that creates a real device is in the `OpenAL` xUnit collection and runs serially; parallel devices corrupted each other's error state.

## Sample 3D game: Orb Run (`samples/Arena3D`, phase 23)

A small playable game built the way a game author would, as a test of the engine from outside. **Rules** are plain code (`OrbGameSession`: 90 s clock, 100 points per orb, bonus per second left, a 5 s penalty for falling; unit-tested). **Components** `Orb` (pick-up radius) and `OrbBob` (bob and spin), systems `OrbCollectSystem` (fixed step after physics: any orb within its radius of the `CharacterController3D` entity is destroyed through a `CommandBuffer` and reported by a callback) and `OrbBobSystem` (per frame). **The scene** (`scenes/arena.scene.json`: floor, 8 stepped platforms, 12 orbs as prefab instances, sun, two lamps, the player capsule) is generated data; step heights are 1 m, within the controller's jump (5.5 m/s, gravity 9.81 gives about 1.5 m). **Camera**: an `OrbitCamera` around the player, turned by the mouse while the right button is held, zoomed by the wheel, eased toward the player's *interpolated* position in `Draw` (never `Update`); W/A/S/D walk relative to where it looks. Falling below y = -6 resets the player (and its `PreviousTransform` and velocity) to the spawn and calls `PlayerFell`. Sound effects (`sounds/*.wav`, made by `tools/make-arena-sounds.ps1`) play through the `Sfx` mixer group; the win/lose jingle plays on the frame the phase changes. `ProceduralTextures.Checker` was added to the engine because the game needed a floor texture without a file. Gaps the game showed are listed in `tasks.md` (phase 23).

## Sample game rules (`samples/Platformer`)

- **Split of responsibilities**: `GameSession` (pure: lives, score, coins, clock, `GamePhase`) owns every rule and has no engine types. `InteractionSystem` (fixed group, after `PhysicsSystem`) only detects hero overlaps (`BoxCollider.GetBounds` / `Aabb.Overlaps`) with `Coin`, `Patrol` (the creature marker) and `Goal` entities and reports events to the session; removals go through a `CommandBuffer` after the queries. A stomp = hero moving down with its feet above the creature's middle; anything else is a hit (the hero is put back at `GameSession.RespawnPoint`, standing still, with its `PreviousTransform` cleared; the 1.5 s invulnerability covers whatever stands there; a hit that ends the run does not move it). `PlatformerGame.Flow.cs` ticks the session each frame, zeroes the hero's `PlatformerIntent` once the run is over, swaps the exit door art when the last coin is taken, blinks the hero while invulnerable, and restarts by `World.Clear()` + `Scenes.LoadFile` (the same path as quick-load, which also re-syncs the coin count from the coins left in the world).
- **Pause**: `Game.IsPaused` (engine) skips the frame and fixed system groups and does not advance the `FixedTimestep`, so no time is owed on resume; `Update`/`Draw`/`Hud` still run. The sample's `PauseMenu` (pure: selection wrap-around and labels, unit-tested) is driven by `PlatformerGame.Pause.cs` from `Update` (keys) and `Hud` (ImGui `Selectable`s, mouse hover/click); while paused `Update` returns early, so the session clock, restart key, quick-save and spawning are frozen too. Pausing is refused once the run has ended (Enter restarts).
- **Checkpoints**: a `Checkpoint { Reached }` component (registered, placed from `checkpoint.prefab.json`, three in the level) is touched by `InteractionSystem`, which raises the flag and calls `GameSession.ReachCheckpoint(position)` (the session only stores the point; the game moves the hero). `SetStart` sets the point at level load, restart and quick-load (the loaded spot counts as a checkpoint because the session is not saved). `Reached` is part of the saved component, so a quick-load keeps raised flags raised; `PlatformerGame.Flow.cs` swaps the flag art from it each frame like the door. Decision: respawn replaced the old knockback, because with knockback a hit left the hero standing in the danger; the cost is that an early hit sends you to the start.
- **High scores**: `HighScores` (pure ranking plus JSON file; best 5, ties rank below the older run, scores <= 0 never recorded) with `ScoreEntry`. `PlatformerGame.Scores.cs` loads `saves/highscores.json` (next to the exe, outside `Assets/`, like the quick-save) at start, submits a run once when its phase leaves Playing and saves only when it earned a rank; the end message lists the table. Decision: a damaged file is player data, so the game logs an Error and starts with an empty table instead of refusing to start (`HighScores.Load` itself still throws, naming the file); loading re-submits every entry so a hand-edited file is re-sorted and trimmed.
- **Content as data**: `coin.prefab.json` and `goal.prefab.json` plus scene entries that override only the position; `Coin` and `Goal` are registered components, so quick-save/load and the inspector handle them with no extra code. The locked/open door is two cells of `items.png`, chosen by setting `Sprite.Source`.
- **UI**: `Game.Hud()` (new hook, called every frame before the debug panels, so it survives F1) draws the status line and end message with ImGui windows flagged no-decoration/no-input; the font scale is set per window.

## Assets

`AssetManager` (Core) caches by normalised relative path per asset type, using registered `IAssetLoader<T>`s; `AssetHandle<T>` is a 1-based int id (0 = invalid) into a per-type `AssetStore<T>`. **Hot-reload**: `AssetManager.Reload(name, fullPath?)` re-runs the loader and swaps the result in under the same handle (load first, then swap, then dispose the old one, so a broken file throws and leaves the old asset); `AssetHotReloader` (Core) watches a folder with a `FileSystemWatcher` whose events only enqueue, and the game loop calls `Poll()` once per frame (reloading a texture calls GL, so it must run on the context thread): a file is reloaded after `QuietSeconds` (0.3) without further events (editors write in several steps), a locked file is retried up to `MaxAttempts`, files the game itself just wrote are skipped via `Ignore` (the editor does this when it saves a tile layer), and files that are not loaded assets (scenes, scratch files) are ignored. `Game.HotReloadRoot` (null = off; the sample returns its project `Assets` folder, which is not the copy beside the exe) turns it on, so editing art in the project updates the running game. Limits: consumers must look the asset up through its handle each use (sprites, tiles and layers do); something built from the old asset and kept (the hero animation machine copied into `HeroAnimationSystem`, the collision grid built from the ground layer) is not rebuilt until restart or Play. `Add(name, obj)` registers procedural assets. `Game.Assets` roots at `<exe dir>/Assets`; sample assets are copied there by `Platformer.csproj`. The manager owns and disposes `IDisposable` assets.

## Rendering pipeline

- **Post-processing** (`Engine.Rendering/PostProcessing`): `RenderTarget` = framebuffer object + `Texture2D` colour attachment (RGBA8, linear filter; `Resize` recreates it). `FullscreenQuad` draws one oversized triangle from `gl_VertexID` (no vertex buffer, only the empty VAO core profile requires), and its vertex source is shared by every effect, which supplies `vUv`. `PostProcessChain` owns two window-sized targets: `BeginScene` binds target 0 when any effect is enabled, `EndScene` runs the enabled effects ping-ponging between the targets, the last writing to framebuffer 0. A shader cannot read what it writes, hence two targets. Textures sampled from a target are not flipped: render and sample share GL's bottom-left origin. `Game` resizes the chain from the window's resize event, times it as the `Post process` profiler section and disposes it after `Unload`.
- **Scene targets, HDR, MSAA and pixel-perfect (phase 19)**: `RenderTargetFormat` (HDR 16-bit float, depth, stencil, samples, filter) describes a `RenderTarget`. The chain owns one **scene target** (depth, multisampled when `Samples > 1`) and two plain **ping-pong targets**; `Resolve()` averages a multisampled scene into its texture, then effects run source -> ping-pong, never drawing into the scene target (**decision and bug found in the window:** with two shared targets the second effect drew into the multisampled buffer and the next effect read the stale resolve, so every effect after the first silently vanished). `Hdr` rebuilds all targets as RGBA16F, `PostProcessContext.IsHdr` tells effects not to clamp (`LightingEffect` builds an HDR light map and skips its `min(.,1)`), and `ToneMapEffect` (Reinhard/ACES/clamp + exposure) goes last. Pixel-perfect: `SetPixelPerfect(w, h)` makes every target game-resolution with Nearest filtering; the last effect writes to a ping-pong target and `Present` draws it to the window at `PixelPerfectLayout` (largest whole scale, centred, black bars, fractional only if the window is smaller). The game sets `Camera2D.ViewportSize` to the game size and `PixelSnap = true`, which rounds the camera, sprite and tile-layer origins to whole pixels (`Camera2D.Snap`); mouse input maps through `PixelPerfectLayout.WindowToGame`. The editor assumes window-pixel picking, so the Platformer leaves pixel-perfect while editing. Any one of Hdr, Samples > 1 or pixel-perfect redirects the scene even with no effect enabled; with none of them and no effect the scene still draws straight to the window.
- **Effects**: `SinglePassEffect` (base: one shader, `SetUniforms` hook) for colour grade and vignette; `BloomEffect` implements `IPostEffect` itself (bright pass to a half-resolution target, N rounds of separable 9-tap Gaussian, composite). Settings are public properties; `Runtime/Inspector/PostEffectsPanel` edits them by reflection through `FieldEditor`.
- **Lighting**: `LightingEffect` (first in the chain) rebuilds a screen-sized light map each frame: clear to `Ambient`, then a `SpriteBatch` pass with `SpriteBlend.Additive` (blend `SrcAlpha, One`) draws one tinted radial-gradient quad per `Light2D` in view (gradient texture from `LightMath.BuildGradientPixels`, falloff `(1 - d^2)^2`), through the scene camera so lights align with sprites. The composite shader outputs `scene * lightMap * Exposure`. Decision: a light-map multiply rather than per-sprite lighting, because its cost does not grow with sprite count and the sprite renderer is untouched; the price is no shadows and no normal maps.
- **Light shadows (phase 19)**: walls come from `IShadowCasterSource`s listed in `LightingEffect.ShadowSources`: `BoxShadowCasterSource` (entities with `ShadowCaster2D`, registered by default) and `Tilemaps.TileShadowCasterSource` (solid tiles of layers with `TileLayerRenderer.CastsShadows`, read only near each light and only where a solid tile touches an open one). A `ShadowEdge` has the solid on its left, so its outward normal is on the right; **a light only casts shadow from walls that face away from it** (`ShadowMath.FacesAwayFrom`), which keeps the front of a platform lit and puts the darkness behind it (extruding every wall instead would shade the platform's own face). Each such wall is pushed away from the light along the rays through its end points to `2 x radius` (`ShadowMath.TryExtrude`). The light map target has a stencil buffer; a light that has walls in reach flushes the batch, clears the stencil, stamps the shadow triangles with colour writes off (`ShadowVolumeRenderer`, a plain 2D triangle drawer), then draws its gradient sprite where stencil == 0. Lights with no wall in reach stay in the shared additive batch. Hard-edged by design; soft shadows would blur the stencil result or sample several light positions. In the window the shadows are clearly visible only when a light is close to walls: `tools/drive-shadows.ps1` shows the on/off pair (verified once with a temporary light and box in the scene).

- World space: X right, Y up, Z draw order (larger = in front). `Camera2D` zoom 1 = 1 world unit per pixel; `GetViewProjection()` is row-vector `Matrix4x4`, uploaded to GL without transpose and used as `uViewProjection * vec4(pos, 1)`.
- `SpriteQuad.Write` (pure, tested) builds 4 vertices from a `SpriteDraw`; `SpriteBatch` fills a `SpriteVertex[]` (max 8192 sprites, 16-bit indices), uploads with `glBufferSubData`, draws with a static index buffer, flushing on texture change. Alpha blending on, depth test off. Built-in GLSL 330 shader in `SpriteShaderSource`.
- Texture space: (0,0) top-left, image row 0 is the top. Window framebuffer size is assumed equal to window size (inferred; not tested on high-DPI displays).
