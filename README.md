# CSharpGame

A small **2D game engine written in C#**, built to learn how engines work and designed so **3D can be added later**. The core systems (ECS, game loop, sprite batching, input mapping, asset management) are written from scratch; libraries are used only for plumbing such as windowing, OpenGL bindings, image decoding and the debug UI.

The first game it is being built for is a platformer.

> **Status:** work in progress. Phases 1 to 7 of 10 are done (see the [roadmap](#roadmap)).

## Features

- **Fixed-timestep game loop** with an interpolation factor, so simulation is deterministic and independent of frame rate
- **Custom sparse-set ECS**: generational entity handles, typed component pools, 1 to 3 component queries with `ref` access, deferred changes through a `CommandBuffer`, ordered system groups
- **Batched sprite renderer** (OpenGL 3.3 core): one draw call per texture run, tint, pivot, rotation, flip and sprite-sheet regions
- **2D camera** with zoom, rotation and screen-to-world conversion
- **2D physics and platformer feel**: gravity, swept AABB-vs-tile/box collision (no tunnelling), and a character controller with acceleration, coyote time, jump buffering, variable jump height and heavier falling; tunable live from the debug UI
- **Tilemaps**: sparse chunked tile layers over a texture atlas, drawn only where the camera looks, in background and foreground passes, with collision derived from the same layer
- **Sprite animation**: frame clips (loop, once, ping-pong) and a data-driven state machine: gameplay writes parameters like `Speed` and `Grounded`, the graph chooses idle, run, jump or fall
- **Scenes and prefabs**: save and load the whole world as JSON; entity templates with merge-style overrides and inheritance; assets referenced by name; loading is all-or-nothing, so a bad file never leaves a half-built scene. Levels, tile sets and animation graphs are plain data files
- **Input mapping**: named actions and axes (`"Jump"`, `"MoveX"`) bound to keys and mouse buttons, with per-frame pressed/released edges
- **Asset manager** with typed integer handles, per-path caching and automatic disposal
- **Dear ImGui debug overlay** (FPS, fixed steps, entities, assets, audio device; toggle with `F1`) that games can extend with their own panels
- **Entity inspector**: browse every entity, edit any component's fields live (reflection over the registered components), add and remove components, create and destroy entities
- **Profiler**: every system and game hook is timed per frame (table plus rolling frame graph); games add their own sections
- **Post-processing**: render-to-texture chain with bloom, vignette and colour grading, all tunable live in a "Post effects" window; zero cost when no effect is enabled
- **2D lights**: `Light2D` point lights (colour, intensity, radius) rendered into a light map and multiplied over the scene, with a configurable ambient level
- **OpenAL audio**: WAV loader, 32-voice pool with oldest-voice stealing, per-sound volume and pitch, silent fallback when no device exists
- **3D-ready math**: transforms are `Vector3`/`Quaternion`; Z is draw order in 2D
- Unit-tested core (ECS, input, assets, timing, camera and sprite-quad maths)

### The sample

The `Platformer` sample is a data-driven tilemap level (see `samples/Platformer/Assets`: scene, prefabs, tile layers, tile set and animation graphs are all JSON) with an animated crowned hero you run and jump with, and patrolling creatures. The hero carries a warm lantern and three coloured lamps (`Light2D` entities in the scene file) light the level; bloom and a vignette are on. The pixel art is generated by `tools/make-sprite-sheets.ps1`. The "Hero feel" panel shows the animation state and lets you tune speed, jump, coyote time, jump buffer and gravity live.

| Input | Action |
|---|---|
| `A` `D` / left and right arrows | Run (the camera follows) |
| `Space` / `W` / up arrow | Jump (hold for a higher jump) |
| Left mouse button | Spawn 5 creatures at the cursor |
| Mouse wheel, or `Q` / `E` | Zoom out / in |
| `R` | Reset the camera |
| `F5` / `F9` | Quick-save the whole world to a scene file / quick-load it |
| `F1` | Toggle the debug UI (Engine, Inspector, Profiler and Post effects windows) |

The hero plays jump and landing sounds and each spawn click plays a blip; the sounds are generated by `tools/make-sounds.ps1`.

## Project layout

```
src/
  Engine.Core/        ECS, fixed timestep, Transform, input state + action map, asset manager (no GPU dependencies)
  Engine.Platform/    Silk.NET window, OpenGL context, input adapter, ImGui controller
  Engine.Rendering/   Shader, Texture2D, SpriteBatch, Camera2D, Sprite component, sprite render system, render targets, post-processing effects, 2D lights
  Engine.Physics2D/   AABB, tile grid, swept collision solver, physics system, platformer controller
  Engine.Tilemaps/    Chunked tile layers, tile sets, layer-to-collision builder, tile render system
  Engine.Animation/   Animation clips, state machine, animator component and system
  Engine.Scenes/      JSON scenes and prefabs: component registry, scene serializer, merge overrides
  Engine.Audio/       WAV decoder, audio clip asset, voice pool, OpenAL device (and a silent fallback device)
  Engine.Runtime/     Game base class and loop, debug overlay, entity inspector, profiler panel
samples/
  Platformer/         The first game, consuming the engine like any game project would
tests/                xUnit tests, one project per module
tools/                PowerShell scripts to run, drive and screenshot the sample
```

Dependencies point one way: `samples -> Runtime -> (every engine module)`, `Tilemaps -> (Rendering, Physics2D)`, `Animation -> Rendering`, and everything else `-> Core`. `Runtime` is the only module that knows about all the others, so it registers the engine's components and asset loaders. `Engine.Core` and `Engine.Physics2D` never reference windowing, OpenGL or Silk.NET, and the tile and animation maths is pure too, so the simulation and content logic is unit-testable without a GPU.

## Writing a game

Subclass `Game`, bind your inputs, register systems, and override the hooks you need:

```csharp
public sealed class MyGame : Game
{
    public MyGame() : base("My Game")
    {
        Actions.BindAxis("MoveX", KeyCode.A, KeyCode.D);

        FrameSystems.Add(new PlayerInputSystem(Actions)); // read input once per frame
        FixedSystems.Add(new MovementSystem());           // simulate at a fixed rate
    }

    protected override void Load()
    {
        // GL is ready: create GPU resources, load assets, spawn entities.
        var texture = Assets.Load<Texture2D>("hero.png");
    }
}
```

The per-frame order is: frame systems, `Update`, then N fixed steps (fixed systems, `FixedUpdate`), then draw and render systems, then the ImGui overlay. Read input in per-frame code and latch it into components, because fixed steps can run zero or several times per frame.

## Design rules

The codebase follows a few strict conventions, several enforced by the compiler:

- One type per file (build error)
- XML documentation on all public members (build error)
- Large classes split into partial files by topic
- SOLID, with dependencies on abstractions at layer boundaries
- Components are plain data; behaviour lives in systems
- No allocations in per-frame hot paths

Details live in [`CLAUDE.md`](CLAUDE.md) and the [`.claude/knowledge/`](.claude/knowledge) folder (architecture, conventions and feature map).
